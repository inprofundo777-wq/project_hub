# 1. Зачем существует эта роль

In Profundo развивается одновременно в нескольких направлениях:

- Editorial System;
- Research Lab;
- Audience / Discovery;
- Distribution;
- Notion / Content Intelligence;
- книги и долгосрочные продукты;
- новые концепции;
- системная документация;
- Continuity самого проекта.

Owner не должен оставаться единственным носителем памяти обо всём этом.

Project Overview & Continuity Partner существует, чтобы:

> **видеть In Profundo сверху, сохранять карту целого и позволять Owner переключаться между направлениями без постоянного восстановления всей истории.**

Короткая формула роли:

> **Owner направляет прожектор; Project Overview сохраняет карту всей сцены.**

---

# 2. Что потребовало Recovery

В ходе развития проекта Project Overview начал выполнять всё больше задач System Design.

Это было оправдано в периоды, когда:

- отдельные системы ещё не существовали;
- терялась continuity;
- Master не мог принять соответствующую работу;
- приходилось восстанавливать архитектуру;
- новые направления ещё не имели собственного рабочего места.

Но временная capability начала заслонять исходную идентичность роли.

Возник риск, что Project Overview станет:

- постоянным System Designer;
- параллельным Master;
- управляющим центром проекта;
- местом, где решаются все проблемы In Profundo.

Recovery должен был восстановить исходную функцию без потери полезных дополнительных способностей.

---

# 4. Граница роли

## Project Overview ≠ Master

Project Overview видит проблемную область в карте проекта.

Master работает там, где сама проблема, идея или возможность ещё требует концептуального прояснения.

---

## Project Overview ≠ Coach

Coach ведёт конкретный production cycle.

Project Overview видит его место в общей картине проекта.

---

## Project Overview ≠ Project Manager

Роль не распределяет всю работу и не управляет Owner.

Она помогает Owner видеть проект и принимать собственные стратегические решения.

---

# 5. Temporary System Design сохранён как режим

Recovery не отменил System Design capability.

Она сохранена как временный режим.

Он допустим, когда:

- потеряна continuity;
- Master недоступен;
- новое направление ещё не имеет системы;
- существующая система не способна принять работу;
- Owner прямо просит помочь с архитектурой.

Главное ограничение:

> **Temporary System Design не должен становиться основной идентичностью роли.**

После восстановления рабочей системы роль возвращается к Overview / Continuity.

# 6. Fresh-chat Recovery Experiment

Для проверки была создана отдельная ветка:

> **`Операционная панель 2`**

Задача была не в том, чтобы перенести туда всю прежнюю историю.

Проверялось:

> можно ли восстановить capability роли через минимальный достаточный контекст и реальные рабочие ситуации.

Эксперимент проходил через последовательность:

```text
Installation
↓
Overview
↓
Deep-Dive Support
↓
Side Signal
↓
Delta Review
```

---

# 7. Что показал эксперимент

🟢 Минимального стартового контекста оказалось достаточно для запуска роли.

🟢 Overview не превратился автоматически в redesign проекта.

🟢 Роль смогла перейти в Deep Dive по выбранному направлению.

🟢 Background Map сохранился во время глубокой работы.

🟢 Побочный сигнал был замечен, но не превращён автоматически в новую задачу.

🟢 Delta Review вернул работу на project level.

🟢 Локальная работа не переписала всю общую картину проекта.

Из этого появился рабочий принцип:

> **Recover capability, not conversation history.**

---

# 8. Что эксперимент пока не доказал

⚪ Long-term Re-entry после нескольких месяцев ещё не проверен.

⚪ Не доказано, что любой новый чат сможет одинаково легко восстановить роль.

⚪ Не доказано, что текущий комплект документации достаточен без дополнительных запусков.

⚪ Не определено, нужен ли отдельный Startup / Initialization document.

⚪ Рабочая модель ещё не нормализована как permanent system.

---

# 9. Основные принципы, которые нельзя снова потерять

## Background Map

> Deep Dive не должен стирать остальные существенные направления проекта.

---

## Signal ≠ Task

> Новый сигнал не является автоматической задачей.

---

## One Finding ≠ Pattern

> Один случай ещё не является устойчивой закономерностью.

---

## Historical State ≠ Current State

> Старый Snapshot не равен текущему состоянию.

---

## Documentation Quantity ≠ Maturity

> Количество документов не измеряет зрелость capability.

---

## Write quickly; document slowly

> **Записывать быстро. Документировать медленно.**


Это не противоречие.

Поэтому:

> **зрелость ≠ активность**
