## 2. Portable Coordination Patterns

**Переносимая практика ≠ перенос роли ≠ перенос authority ≠ перенос предметной компетенции.** Следующая таблица описывает способы работы, которые можно заново закрепить в конкретном поручении.

| Элемент Installation | Что переносится | Условие межсистемного применения |
|---|---|---|
| Scope | Один вопрос, предел, исключения и достаточный конечный результат | Общий owner и владельцы узлов согласовали границы; цель не обещает заранее позитивного вывода |
| Stages | Различимые операции и условия перехода | Стадии следуют реальным зависимостям; не копируют книжный цикл Lab |
| Dependencies | Предпосылка, владелец, влияние на следующие операции | Отдельно показать отсутствие источника, компетенции, authority и ресурса |
| Assignments | Ограниченный вход, задача, выход и возврат | Назначение совместимо с локальным мандатом узла; внешний участник действительно принял поручение |
| Output Contracts | До исполнения определить, какой результат нужен принимающей стороне | Договор согласован отправителем и получателем; предметная методика остаётся локальной |
| Acceptance criteria | Проверяемые условия завершения | Для каждого условия названы evidence и компетентный принимающий |
| Stop Conditions | Остановить операцию при материальном выходе за предел | Названо, что именно блокируется, и кто разрешает восстановление |
| Return Routes | Вернуть дефект тому, кто вправе его исправить | Есть согласованный адресат, порядок спора и конечный Owner gate |
| Version binding | Закрепить конфигурацию назначения и редакции входов | Живой README используется для навигации, immutable target — для решения |
| Source / provenance | Сохранить путь источника, результата, исправления и принятия | Узлы могут иметь разные формы записи; существенные связи остаются восстановимыми |

### Stage Coordination без авторства всех выводов

Один Lead удерживает проект через **карту обязательств и переходов**, а не через собственное производство каждого ответа. Он проверяет: есть ли принимаемый объект, кто его произвёл, какую редакцию проверили, какие ограничения остаются, какая зависимость закрыта и что разрешено дальше. Автор и предметный принимающий сохраняют ответственность за суждение.

Для независимых capabilities этот механизм возможен, если координатор имеет право запрашивать согласованные outputs и удерживать **проектный переход**. Это не даёт ему права менять методы узла или управлять всей деятельностью его owner.

Граница возникает, когда координатор:

- выбирает, какая из несовместимых предметных интерпретаций истинна;
- объявляет два термина разных disciplines эквивалентными;
- оценивает применимость чужого результата к новой популяции или ситуации;
- добавляет причинную, нормативную или практическую связь;
- решает, что предметную проверку можно опустить, хотя договор требует её.

Это уже содержательное решение. Оно требует отдельного автора, компетенции и приёмки; координационный мандат его не покрывает.

Последовательность Biblical → Clinical → Synthesis → Application → Product возможна как пример, но не должна становиться универсальным pipeline. Библейский и клинический узлы могут работать параллельно; зависимый синтез ждёт конкретных нужных результатов. Исследовательское сообщение может завершиться без применения, а один принятый синтез может разветвиться на несколько продуктов.

## 4. Cross-System Output Contract Model

### 4.1. Возможность и ограничение

Да, договор результата может стать границей между независимыми owners. В Lab он конкретизирует Protocol ниже общих управляющих документов. Межсистемный договор дополнительно должен установить, **кто обязан предоставить результат, кто вправе его принимать и как согласуется несовместимость локальных правил**. Такая институциональная функция нынешним OC сама по себе не обеспечена.

Предлагается использовать OC как интерфейс конкретного поручения, не как общий закон над всеми системами. Приёмщик не может задним числом добавить требование, чтобы получить удобный вывод.

### 4.2. Минимальное содержание

| Блок | Обязательное содержание |
|---|---|
| Стороны и authority | Отправитель, получатель, owner результата, предметный проверяющий; основания их полномочий и согласие на поручение |
| Вопрос и объект | Подвопрос, тип результата, область/корпус, исключения; что считается достаточным отрицательным или ограниченным результатом |
| Закрепление | Версии входов, локальной процедуры, договора, назначения; точный target результата |
| Основания | Источники/локаторы, существенный reasoning, тип evidence, контрсвидетельства и пробелы |
| Предел вывода | Confidence в локальном значении, ограничения, контекст/актуальность, запрещённые выводы и допустимое использование |
| Приёмки | Какие условия проверяет координатор; какие — предметный owner/reviewer; точные targets их verdicts |
| Переход | Кому передаётся объект и какой следующий шаг допустим; что остаётся заблокированным |
| Возврат и изменение | Классы дефектов, исправляющий owner, порядок спора, замены редакции и уведомления зависимых сторон |

Для небольшой задачи это может быть несколько абзацев в одном assignment. Отдельный файл OC для каждого действия не требуется.

### 4.3. Что проектировать заново

Потребуются взаимное принятие интерфейса, правила межсистемного спора, ответственность за новый связующий вывод, порядок обновления зависимых outputs и распределение права перехода. Нужны также определения локальных статусов: «высокая уверенность» источниковой атрибуции не равна высокой уверенности эффективности практики.

Синтез получает не «истину вообще», а локальные результаты вместе с границами. Для каждого нового общего утверждения следует сохранить родительские findings и версии, основание их соединения, новые предпосылки и конкретный предмет проверки. Проверенные узлы **не делают автоматически проверенной связь между ними**.

Application получает принятый синтез с его ограничениями; Product / Editorial Handoff добавляет аудиторию, функцию продукта, разрешённые действия и обязательные reviews. Узкая Publication System получает уже approved publish-ready Source. Эта граница согласуется с консультацией Publication Master и не требует расширять Publication.

## 5. Acceptance / Block / Return Model

### 5.1. Пять различимых решений

| Приёмка | Вопрос | Кто решает | Чего решение не устанавливает |
|---|---|---|---|
| Contract acceptance | Выполнены ли согласованные требования к объекту и record? | Координатор в явно разрешённой процедурной части | Истинность всех предметных claims |
| Subject acceptance | Достаточны ли источники, методы и основания локального суждения? | Компетентный предметный принимающий; независимый reviewer при соответствующем trigger | Корректность будущего междисциплинарного переноса |
| Synthesis acceptance | Обоснованы ли новые связи, не скрыты ли несовместимости? | Назначенный принимающий синтеза с необходимыми reviewers переходов | Допустимость практического использования |
| Application acceptance | Допустим ли конкретный способ использования для названной аудитории/контекста? | Владелец применения и профильные reviewers | Готовность текста, доставка и доказанная польза сверх проверенного scope |
| Project progression | Закрыты ли зависимости и есть ли authority следующего шага? | Координатор в делегированном envelope; иначе Owner | Новый предметный verdict или разрешение всех последующих стадий |

Координатор может принять объект как contract-complete, не принимая его предметно истинным. Но статус должен указывать **предел**: «комплектность проверена; предметное принятие ожидается; для синтеза не допущен».

Если полный договор требует предметного verdict, его отсутствие означает, что договор целиком ещё не выполнен. Можно принять документарную часть или корректный blocked handoff, но нельзя объявить весь OC выполненным. Это различие уже работало в Event 019.

В нынешней Lab принятие по OC не сводится к комплектности: Events 021 и 060 проверяли основания суждений, а Event 072 — семантическую эквивалентность. Поэтому **чистая процедурная приёмка — предлагаемое разделение межсистемного мандата, а не описание всей существующей функции Lead**.

Safeguards: отдельные поля приёмок; версия и scope каждого verdict; отсутствие самопроверки под видом независимости; обязательные ограничения в downstream handoff; правило, что условный verdict с открытым blocking condition не разрешает переход. Предметное принятие остаётся проверяемым и пересматриваемым, а не административным объявлением абсолютной истины.

### 5.2. Block → classify → correct owner → correct → re-accept → continue

| Класс блокера | Куда возвращать | Что может координатор |
|---|---|---|
| Недостающая часть/локатор | Автору соответствующего output | Указать точный договорный дефект и удержать зависимый переход |
| Предметная ошибка/неопределённость | Domain owner и компетентному reviewer | Запросить предметное решение; сохранить спор без собственного разрешения |
| Необоснованная связующая claim | Автору синтеза и проверяющим перехода | Отделить её от принятых локальных findings; заблокировать её использование |
| Применение вне принятого scope | Application owner и профильным reviewers | Вернуть application object; не исправлять практику редакционной формулировкой |
| Нарушение независимости | Владелец назначения проверки | Не засчитывать verdict; запросить действительно независимую конфигурацию |
| Недостаток authority/ресурса | Owner или полномочному локальному владельцу | Подготовить точную развилку: обеспечить, сузить, отложить, закрыть |
| Изменившийся upstream target | Владельцам всех существенно зависимых результатов | Заморозить затронутую приёмку, определить impact и нужный re-check |

Повторная приёмка охватывает возвращённый дефект и возможные новые материальные отклонения, сохраняя уже проверенные части. Модель Events 064 → 071 → 072 показывает, как избежать полного повторения работы. Новая редакция не считается принятой только по номеру R1/R2.

**Где механизм ломается:** у координатора нет согласованного права вернуть результат; узел не принимает obligation; два owners спорят о смысле договора; отсутствует компетентный reviewer; локальные правила не позволяют ожидаемый output; изменение затрагивает уже несколько downstream объектов. Тогда нужен проектный gate с owner решения. Бесконечный RETURN не заменяет сужение или CLOSE.

PARTIAL STOP допустим только при заранее делегированном или отдельно разрешённом продолжении независимой части. Координатор удерживает переход данного поручения; он не приобретает право остановить всю деятельность автономной системы.

### 5.3. Версии и происхождение

1. Закрепить роль/мандат, договор, процедуру, версии inputs и дату конфигурации перед работой.
2. Развести нормативную версию, редакцию output и решение о принятии. Больший номер версии не удостоверяет качество и не меняет статус автоматически.
3. Обозначить supersession: что именно заменено, для каких будущих действий и что остаётся действительным исторически.
4. Сохранять прежние targets по отдельным файлам или immutable commits. Для изменения вывода — новая редакция и решение с rationale.
5. Привязать verdict к проверенной редакции; изменения после проверки требуют оценки влияния.
6. При изменении узла проверить не только его файл, но и использующие его synthesis / application / product. Приёмка новой версии не мигрирует их молча.
7. Поддерживать один текущий паспорт поручения и журнал решений. Паспорт показывает состояние; журнал содержит authority. При расхождении действует последнее полномочное решение, а навигационный долг исправляется.

RQ-RL-002 нельзя перепоставлять через вторую независимую Formation только ради новой организационной схемы. R2 и Installation v0.1 сохраняются; будущая коррекция должна точно назвать преемственность и заменяемый объём. Конституционный вопрос нельзя закрыть одним обновлением версии языка.

## 6. Temporary Coordinator Stress Test

Гипотетический Cross-System Project Coordinator / Lead рассматривается как функция конкретного поручения. Новая роль здесь не создаётся.

| Вопрос | Минимальный ответ |
|---|---|
| 1. Какой authority необходим? | Держать утверждённый scope; согласовывать interfaces; получать outputs/verdicts; вести зависимости и record; возвращать договорные дефекты; удерживать переходы; продолжать заранее разрешённые операции; эскалировать материальные изменения |
| 2. Чем отличается от Lab Lead? | Проектный мандат между автономными owners; нет общего подчинения Director, права назначать все disciplines или применять Lab Methodology как их закон |
| 3. Что принимает сам? | Документарную комплектность, traceability в доступной проверке, точность версии/статуса, корректный blocked handoff, выполнение разрешённых переходных условий |
| 4. Что требует domain acceptance? | Предметный результат, перенос findings в синтез, новые связующие claims, применение. Координатор проверяет наличие и scope компетентных verdicts, не заменяет их |
| 5. Может ли работать без компетенции во всех domains? | Да, при достаточной грамотности для чтения интерфейсов, распознавания предела и запроса проверки. Нет, если ему поручено лично удостоверять чужие claims или незамеченные переходы |
| 6. Какие документы минимальны? | Одна рамка поручения с owner, scope, бюджетом/ресурсами, authority, exit; встроенная матрица узлов/зависимостей и договоры; один текущий вход и журнал. Специализированные verdicts ссылаются на точные targets |
| 7. Где Owner gate? | До нового межсистемного исполнения; при изменении цели/scope/authority, неделегированных расходах или неразрешимом споре; до непорученного application/product; при закрытии по установленному договору |
| 8. Как закрывается? | Достаточный результат, ограниченный/отрицательный итог, DEFER/CLOSE либо точный BLOCK; сохранены outputs, решения и gaps; названы принимающая сторона и судьба обязательств; временный мандат прекращён |
| 9. Когда нужна постоянная capability? | Разные реальные поручения повторяют те же coordination gaps; перенос выдержал fresh recovery; Owner меньше собирает вручную; есть устойчивые задачи поддержки, доступные компетенции и ресурс владельца |

**Минимальное проектное полномочие:** координатор управляет допуском результатов в следующий шаг этого поручения. Для указаний автономному узлу требуется согласованный interface или локальный owner; одна команда Owner не создаёт обязательства у независимой внешней стороны.

Координатор может также составлять синтез только через отдельное назначение с показанной способностью. В таком случае он автор синтеза и не выполняет его независимую проверку. Совмещение функций допустимо; стирание разных решений — нет.

### Нормальное закрытие и цена

Close Package временного поручения содержит: фактический результат против договора, карту приёмок/версий, ограничения, нерешённые вопросы, disposition незавершённых обязательств, owners переданных продуктов, точный следующий gate и Role Exit. Если продукт требует дальнейшей актуализации, её владелец назначается явно; временный координатор не сохраняет бессрочное обслуживание.

Цена временной модели — согласовать стороны и границы, поддерживать зависимые версии, маршрутизировать споры и обеспечить reviewers. Она не равна «одному документу». Без готовых участников настройка может оказаться дороже самой небольшой задачи. Точные часы/стоимость из прочитанного evidence не установлены.

Repeated temporary assignment становится фактически новой ролью, если появляется постоянный intake, общий backlog, бессрочное сопровождение, право назначать чужих исполнителей и повторяющаяся ответственность вне закрываемых поручений. Это триггер явно проверить постоянный мандат и ресурс; не способ легализовать его без решения. Сама повторяемость не доказывает необходимость новой системы: сначала проверить переиспользуемый pattern или capability.

## 7. RQ-RL-002 Architecture Test

Это только мысленный тест координации. Существующий первый обзор L0–L4 и возможная будущая цепочка ниже — разные объекты. Ни один узел не активирован; предметных выводов о депрессии, суицидальности, лечении или пастырской практике здесь нет.

### 7.1. Возможная будущая конфигурация

| Переход / объект | Необходимый договор | Приёмка и риск скрытого authority |
|---|---|---|
| Общий вопрос → biblical/theological node | Точный подвопрос, корпус, предел богословского вывода, версии и return | Lab работает в своём предмете/Scope. Принадлежность узла Lab не разрешает всю межсистемную тему |
| Общий вопрос → clinical / psychological / prevention node | Самостоятельная предметная рамка, метод, допустимые claims, актуальность, owners/reviewers | Нужна реальная предметная компетенция. Нельзя объявить самостоятельную работу вспомогательной лишь по названию |
| Общий вопрос → pastoral / historical node | Описательный/исторический вопрос, источники, контекст и границы | Обзор позиции автора не равен принятию практики; предметный owner назван отдельно |
| Узлы → bounded synthesis | Принятые локальные версии и verdicts; запреты переноса; новые связи и их проверка | Предметные reviewers проверяют перенос своих findings; новый общий вывод требует собственного принимающего и проверки связей |
| Synthesis → application | Аудитория, контекст, конкретный объект применения, допустимые действия и предел | Координатор не выбирает практику вместо competent application owner; описательный синтез не становится intervention |
| Application → product decisions | Отдельная функция и scope статьи/пособия/семинара | Один общий пакет не означает одинаковую пригодность для всех аудиторий и продуктов |
| Product → Editorial | Принятый содержательный Source и Product / Editorial Handoff | Editorial создаёт текст; изменение существенного смысла возвращается upstream |
| Editorial → Publication | Approved publish-ready Source | Публикационная проверка не заменяет предметные и прикладные acceptances |

Один временный координатор способен удерживать карту такой цепочки при согласованных obligations и доступных принимающих. Он не способен единолично удостоверить все её выводы. Если именованных компетентных сторон нет, он удерживает **карту заблокированного маршрута**, а не исполняемый проект.

### 7.2. L0–L4: сохранить / переназначить / не переносить

| Операция Installation v0.1 | Сохранить как pattern | Переназначить при внешней рамке | Не переносить автоматически |
|---|---|---|---|
| L0 — готовность | Проверка конфигурации, источниковедческой способности и независимости до допуска | Кто назначает тест; предметный проверяющий; scope допуска каждой функции | Lab role title как свидетельство clinical/statistical/language competence |
| L1 — обнаружение/отбор | Ограниченный поиск, dispositions, доступ и сохранение отрицательного результата | Локальный owner внешнего поиска и бюджет | Весь внешний поиск под единой Lab authority |
| L2 — картирование | Карточки, локаторы, версии, различение источника и вывода | Языковой и количественный блоки при разрыве способности; собственные локальные controls | Экзегеза, клинический вывод, новые расчёты или прикладная норма из карточек |
| L3 — проверка | Независимость и verdict по точному target | Библиографические/методологические, языковые и будущие предметные проверяющие по своим вопросам | Универсальный Lab Auditor, покрывающий все disciplines |
| L4 — приёмка/закрытие обзора | Самостоятельный ограниченный итог, OC acceptance с пределом и return | Сквозной owner после закрытия внешней карты; Director принимает лишь свой Lab layer при назначении | Закрытие всей темы или автоматический Director ownership над федеративным маршрутом |

Первый обзор пока производит **карту источников и покрытия**, а не принятые локальные предметные conclusions. Будущий синтез не может обращаться с его карточками как с доказанными результатами узлов.

Полезность нынешнего Lead заканчивается там, где требуется новое межсистемное authority, квалифицированное предметное решение, принятие общего связующего вывода или application. L0–L4 помогают сделать эти пределы видимыми, но не закрывают их.

Будущий маршрут обязан сохранить преемственность R2 / Installation v0.1 и разрешить уже выявленную развилку: сужение внутри нынешней Lab, внешнее project-level поручение либо отдельно разработанное изменение предмета Lab. Эта консультация не выбирает маршрут за Owner и не исправляет пакет.

## 8. Contrast Test

Использован мысленный кейс Frame §8: история небольшой общины → достоверная статья, памятный буклет и занятие для молодых участников. Это не запуск исследования, интервью или сбора данных.

| Механизм | Как работает в контрастном кейсе |
|---|---|
| Поручение | Назван период/архив, достаточный итог и общий owner; библейский node не добавляется без реального текстового вопроса |
| Договор результата | Архивные события отдельно от воспоминаний; источники, даты, attribution, расхождения и ограничение полноты |
| Предметная приёмка | Другой читатель оригиналов проверяет существенные даты/атрибуции; составитель истории не выдаёт свою проверку за независимую |
| Синтез | Составитель соединяет проверенные записи, сохраняя спорные свидетельства; не превращает память участника в документально установленный факт |
| Application / Product | Для статьи/буклета достаточно закрытого intent и условий использования личных историй; занятие требует отдельного образовательного решения |
| Block / Return | Неподтверждённая дата возвращается архивному owner; неясное разрешение личной истории — владельцу соответствующего решения; проблема занятия — его автору |
| Версии | Изменение архивного finding проверяется на влияние на текст и занятие; опубликованный буклет не переписывает прошлую evidence base |

**Результат логического теста:** основной pattern сохраняется при меньшей цене ошибки. Специфичны для RQ-RL-002 набор профессиональных компетенций, актуальность и ограничения применения; не сама необходимость различать вывод, проверку и переход.

**Упрощение:** один brief, небольшая таблица архивных findings и встроенные отметки приёмки могут заменить множество stage files. Статья не нуждается в отдельном application cycle, если не содержит проектируемой практики. История общины сама по себе не становится исследованием нынешней Lab.

Мысленный тест показывает логическую переносимость. Он не является real-work validation, не подтверждает нагрузку, экономию времени или достаточность доступных исполнителей.

## 9. Failure Modes

| Failure mode | Диагностический признак | Необходимая коррекция модели |
|---|---|---|
| Избыточный pipeline | Каждая статья получает все исследовательские/прикладные стадии | Активировать только нужные функции; разрешить достаточное завершение без продукта |
| Дублирование Lab Lead | Внутри обычного библейского проекта над Lead поставлен ещё один координатор тех же операций | Использовать действующий Lab маршрут; внешний мост только при реальном межсистемном переходе |
| Временная роль становится постоянной скрыто | Общий intake/backlog и бессрочная ответственность, но нет поддерживаемого мандата | Явно оценить capability, ресурсы и постоянный envelope; не сохранять власть после exit |
| OC превращается в сертификат истины | Все поля заполнены, но ни один компетентный reviewer не принял reasoning | Развести комплектность и предметную приёмку; блокировать dependent use |
| Синтез без владельца | Узлы приняты, а новая связь появилась в заключении координатора | Назвать автора, предмет проверки и принимающего связи; иначе сохранить unresolved |
| Gate bureaucracy | Owner подтверждает каждое исправление в прежнем scope | Делегировать bounded correction и переходы; оставить Owner gates для реальной смены authority/цели/ресурса |
| Owner — скрытый интегратор | Он вручную сводит файлы, выбирает несовместимые claims и напоминает каждому owner | Единый decision brief готовит координатор; предметные споры возвращаются компетентным сторонам; Owner выбирает маршрут |
| Federation разрушает accountability | Каждый утверждает, что отвечал только за свой node; никто не отвечает за утверждение между ними | Отдельная ответственность за связывающий вывод и project-level handoff, без коллективного размытия |
| Authority без competence | Координатор отменяет предметный verdict ради сроков или продукта | Scope принятия фиксируется заранее; reviewer verdict нельзя административно заменить |
| Независимость по названию | Автор меняет роль или пишет вторую внутреннюю оценку | Проверить участие в создании target; независимую проверку выполняет отдельная конфигурация |
| Ложная версия | Latest main / R2 автоматически считается принятым | Привязать status к решению и immutable target; оценить downstream impact |
| Безресурсная архитектура | В таблице названы эксперты, но они недоступны или не приняли assignment | Не обещать исполнение; предложить ресурс, сужение, DEFER/CLOSE |
| Искусственно автономные nodes | Предмет невозможно честно разрезать; interfaces теряют взаимные предпосылки | Вернуть decomposition: совместная постановка/итерация и отдельная компетентная проверка связей |
| Endless RETURN | Возвраты не закрывают недоступную компетенцию или нерешённую цель | Отдельное решение о сужении/остановке; сохранить ограниченный результат |

Нынешняя практика **не поддерживает** сильную гипотезу «достаточно временного координатора и OC — федерация готова». Event 036 уже показал зависимость от подробных указаний, Events 044–047 — необходимость коррекции дизайна и настоящей независимости. Наличие этих механизмов не гарантирует лёгкость исполнения.

Более слабая гипотеза остаётся обоснованной: ограниченное поручение может проверить interfaces без учреждения постоянной системы, если не скрывает отсутствующие authority, expertise и ресурсы.

### 10.2. Предлагаемые deltas Frame
