**Статус:** 🟡 Working / Experimental  
**Версия:** v0.1  
**Дата:** 31 августа 2026  
**Назначение:** хранить незакрытые вопросы развития capability Project Overview & Continuity Partner.

> Этот документ не является backlog проекта In Profundo.  
> Здесь фиксируется только развитие самой роли, её Continuity-инструментов и способности к устойчивому Re-entry.

## Нормативное место

Этот документ является рабочей / экспериментальной документацией Project Overview & Continuity Partner.

Он подчинён:

1. `editorial_system/Constitution/DNA.md`;
2. действующим фундаментальным документам In Profundo;
3. утверждённой архитектуре нормативных уровней.

Документ не создаёт самостоятельной нормативной власти и не может:

- переопределять DNA;
- изменять полномочия Owner;
- окончательно устанавливать мандаты Master, Coach или других ролей;
- заменять будущий Architecture and Authority Framework;
- превращать подтверждённую рабочую практику в норму всего проекта без отдельного принятия.

Формулировки о границах ролей в этом документе следует понимать как working boundaries, подтверждённые текущей практикой и подлежащие последующей сверке с фундаментальным корпусом.

# 3. Главный незакрытый вопрос

## Long-term Re-entry

**Статус:** ⚪ ещё не проверено

Fresh-chat Recovery показал:

> capability можно восстановить без полного переноса старой истории.

Но ещё не доказано:

> можно ли через несколько месяцев открыть существующие документы и продолжить работу без нового Recovery-цикла.

### Что будет считаться evidence

Через значительный промежуток времени:

1. открыть Project Overview в новом чате;
2. использовать существующую документацию;
3. восстановить Background Map;
4. выбрать направление;
5. провести Deep Dive;
6. вернуться на project level;
7. не использовать длинную историю старых чатов как основной источник.

### Возможные результаты

🟢 PASS — документации достаточно.

🟡 PARTIAL — capability восстановлена, но потребовался небольшой дополнительный context package.

🔴 FAIL — пришлось фактически заново восстанавливать роль из истории.

# 4. Startup / Initialization

**Статус:** ⚪ кандидат, не утверждён как отдельный документ

Сейчас новый чат потенциально может запускаться через:

- README;
- Operating Model;
- Decision Memory;
- Project-level Snapshot;
- актуальную Development Map;
- конкретный вопрос Owner.

Нужно проверить, достаточно ли этого.

### Не создавать отдельный Startup-документ только ради полноты.

Отдельный `Startup.md` / `Initialization.md` нужен только если практика покажет повторяющуюся проблему:

> существующие документы слишком велики или неудобны для быстрого запуска роли.

### Возможная будущая функция

Короткий переносимый блок:

```text
WHO YOU ARE
CURRENT PROJECT STATE
NON-NEGOTIABLE BOUNDARIES
BACKGROUND MAP
CURRENT QUESTION
EXPECTED MODE
```

Но пока это только candidate pattern.

# 5. Snapshot practice

**Статус:** 🟡 начинает применяться

Уже принято различение:

> 📸 Слепок хранит понимание.  
> 🚦 Карта развития хранит движение.  
> 📡 Рабочая панель хранит текущую работу.

Нужно проверить эту модель на нескольких разных типах объектов.

### Планируемые случаи

🟡 Project Overview / Continuity — Recovery Snapshot.

🟡 Notion / Content Intelligence — концептуальный Snapshot.

🟡 Book «Тот, Кто остаётся» — концептуальный Snapshot.

🟡 «Взгляд» — Snapshot незрелой идеи.

🟡 Research Lab — новое поколение только после следующей значимой контрольной точки.

### Что проверяем

- действительно ли Snapshot облегчает Re-entry;
- достаточно ли блока координат возврата;
- помогают ли Search Anchors;
- не превращается ли Snapshot в living document;
- не создаём ли мы лишние Snapshot ради архива.

# 6. Development Map practice

**Статус:** 🟡 концепция принята, реальная эксплуатация ещё начинается

Development Map должна отвечать:

> **Что уже созрело и чему ещё предстоит созреть?**

Она должна быть:

- простой;
- визуальной;
- Owner-facing;
- обновляемой минимальным действием;
- не превращённой в KPI.

### Следующий тест

Создать одну общую Development Map In Profundo и проверить:

1. можно ли читать её за несколько минут;
2. понятны ли реальные gaps;
3. можно ли обновлять состояния заменой маркеров;
4. не дублирует ли она Operational Panel;
5. помогает ли выбрать следующую контрольную точку.

# 7. Operational Panel

**Статус:** 🟡 концепция исторически подтверждена, современная форма требует пересмотра

Первый экспериментальный холст операционной панели появился 20 июля 2026.

Его функция была:

- показать активные направления;
- ближайшие задачи;
- незакрытые решения;
- текущий operational focus.

После Recovery стало яснее, что Operational Panel должна быть отделена от:

- Strategic Snapshot;
- Development Map;
- общего Project Map.

### Следующий вопрос

Нужна ли постоянная GitHub-версия Operational Panel или лучше держать её как компактный чат-инструмент?

Пока не решено.

# 8. Coordinates of Return

**Статус:** 🟡 новая практика

Для значимых Snapshot и направлений теперь сохраняются:

- ответственная роль;
- точная ветка;
- связанные ветки;
- ключевые документы;
- Search Anchors;
- Re-entry Question.

### Что нужно проверить

- реально ли Search Anchors помогают через месяцы;
- достаточно ли точного названия ветки;
- нужно ли сохранять дату/период разговора;
- нужны ли прямые ссылки на чат, если продукт это позволяет;
- какие координаты оказываются лишними.

Не нормализовать формат до накопления нескольких реальных случаев.

---

# 9. Decision Memory

**Статус:** 🟡 создано, требует практической проверки

Нужно установить:

- какие решения действительно стоит хранить;
- когда запись становится слишком мелкой;
- не превращается ли Decision Memory в общий журнал проекта;
- помогает ли он в новом чате;
- стоит ли позже разделить role decisions и project-level decisions.

Пока сохраняется принцип:

> записывать только то, потеря чего приведёт к повторному Recovery, неверной маршрутизации или размыванию роли.

---

# 10. Project Map

**Статус:** 🟡 рабочая версия

Project Map должен оставаться Background Map, а не вторым Strategic Snapshot.

Нужно наблюдать:

- насколько быстро устаревают перечисленные направления;
- какие области являются действительно постоянными;
- стоит ли отделить Stable Map от Current Areas;
- насколько полезна карта связей;
- не нужно ли сделать её компактнее после нескольких реальных запусков.

---

# 11. Temporary System Design Mode

**Статус:** 🟡 граница сформулирована, требует наблюдения

Recovery показал необходимость сохранить System Design capability.

Главный риск:

> роль снова начинает измерять свою полезность количеством системных документов.

### Наблюдать

- насколько легко роль выходит из System Design;
- не присваивает ли ownership;
- не создаёт ли документацию без evidence;
- не вытесняет ли Master;
- не превращает ли каждый finding в architectural problem.

### Exit test

После System Design роль должна быть способна вернуться к обычному Overview без необходимости продолжать redesign.

---

# 12. Relationship with Master

**Статус:** 🟡 рабочая граница сформирована

Текущее различение:

> Project Overview видит проблемную область в карте проекта.  
> Master проясняет проблему на границе неопределённости.

Нужно проверить на реальных handoff:

- достаточно ли понятен Transfer Threshold;
- не передаётся ли задача Master слишком рано;
- не продолжает ли Project Overview прорабатывать концепцию после передачи;
- возвращается ли результат Master обратно в project-level map.

---

# 13. Relationship with Owner Journal

**Статус:** 🟡 модель сформирована

Owner Journal сохраняет сырые наблюдения.

Project Overview должен уметь:

- не комментировать их автоматически;
- не превращать их в Task;
- позже замечать repeated signals;
- отличать pattern от единичного finding.

### Будущий evidence

Проверить несколько случаев, когда observation из Journal через время действительно превратился:

```text
Observation
→ repeated signal
→ interpretation
→ decision / development
```

# 14. Documentation load

**Статус:** 🟡 зона риска

Recovery уже породил несколько документов.

Это оправдано потерей continuity, но существует риск создать новую административную нагрузку.

### Guardrail

Новый постоянный документ должен отвечать хотя бы одному вопросу:

- какую capability он сохраняет;
- какую потерю предотвращает;
- какой повторный Recovery устраняет;
- какую передачу делает легче;
- какой Owner load снижает.

Если ответ отсутствует — документ не нужен.

# 18. Условие Normalization

Не переводить комплект из `Working / Experimental` в более стабильный статус только потому, что документы написаны.

Normalization становится оправданной, если:

1. модель использовалась в нескольких реальных ситуациях;
2. fresh-chat запуск повторяем;
3. Deep Dive + Delta Review повторяемы;
4. документация помогает, а не увеличивает Owner load;
5. не обнаружены существенные role-boundary failures;
6. выполнен хотя бы один meaningful Re-entry после паузы.

---

# 19. Следующая контрольная точка

Следующий Development Review роли проводить при одном из событий:

- новый чат не смог корректно восстановить capability;
- произошёл существенный конфликт с Master / Coach;
- роль снова ушла в постоянный System Design;
- накопилось несколько Snapshot и выявился повторяющийся defect;
- проведён long-term Re-entry;
- Owner ощущает, что Continuity снова требует слишком много ручной памяти.

До этого документ обновляется только при material evidence.

# 20. Normalization Trigger

Документация Project Overview & Continuity Partner остаётся `Working / Experimental`, пока практика не даст достаточных оснований для её окончательной сверки и утверждения.

## Триггер обязательного Review

Запустить `Project Overview Documentation Review`, когда выполнено хотя бы одно из двух условий:

### A. Появился фундаментальный архитектурный документ

Принят или подготовлен к утверждению `Architecture and Authority Framework` либо другой фундаментальный документ, который нормативно определяет:

- место Project Overview;
- границы Master;
- границы Coach;
- ownership систем;
- правила межсистемной маршрутизации.

В этом случае документация Project Overview должна быть сверена с ним до получения стабильного статуса.

### B. Накоплено достаточное практическое evidence

Выполнен meaningful long-term Re-entry:

- направление или сама роль возвращены после существенной паузы;
- существующая документация использована для восстановления контекста;
- Background Map удалось восстановить без реконструкции длинной истории;
- проведён реальный Overview / Deep Dive;
- роль корректно вернулась на project level.

После этого появляется основание проверить, действительно ли документация описывает работающую capability, а не только удачный Recovery experiment.

---

## Дополнительные ранние триггеры

Review проводится раньше, если обнаружен:

- конфликт Project Overview с Master или Coach;
- неясный ownership;
- повторяющийся routing failure;
- необходимость обходить существующую документацию;
- существенный рост Owner load;
- новая практика, противоречащая Operating Model;
- material change самой роли.

---

## Результат Review

Review должен закончиться одним из трёх результатов:

🟢 **Normalize** — модель подтверждена практикой и согласована с фундаментальной архитектурой; документацию можно перевести в стабильный статус.

🟡 **Revise and Continue Testing** — модель в основном работает, но требует изменений и дополнительного evidence.

🔴 **Reopen Architecture** — обнаружено фундаментальное несоответствие роли или её места в системе.
