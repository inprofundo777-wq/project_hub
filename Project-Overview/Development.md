## 2. Закрытый audit cycle

Project audit установил, что прежняя документация верно сохраняла Recovery core, но была уже фактической capability. В ней недоставало:

- developmental awareness;
- architecture awareness;
- horizon preservation;
- Scale Recovery;
- чёткого различия Task Exit и Role Exit;
- корректной карты Owner / Master / Coach / Strategist / Research;
- передачи временно восстановленной capability следующему owner/leader;
- зрелого Snapshot как developmental provenance.

Эти gaps представлены в revised candidate v0.2. Нормализация считается завершённой только после Owner verification.

## 3. Long-term Re-entry

**Статус:** ⚪ отдельный отложенный validation test

Нужен тест после значительного временного интервала, в котором новый или очищенный рабочий контекст получает:

1. `README.md`;
2. `Operating_Model.md`;
3. `Decision_Memory.md`;
4. актуальную Development Map;
5. post-audit Snapshot;
6. конкретный вопрос Owner.

Тест должен восстановить:

- identity и boundaries роли;
- Background Map;
- current project state;
- один осмысленный Deep Dive;
- возвращение на project level;
- корректный следующий маршрут.

Не использовать длинную историю старой ветки как основной источник.

### Verdict scale

- 🟢 **PASS** — capability восстановлена без дополнительной реконструкции;
- 🟡 **PARTIAL** — потребовался небольшой дополнительный context package;
- 🔴 **FAIL** — фактически потребовался новый Recovery из истории.

Текущий перенос зрелой ветки в Work подтверждает техническую continuity чата и GitHub, но не заменяет этот тест: история была унаследована, а интервал не был значительным.

## 4. Startup / Initialization

**Статус:** ⚪ не создавать без evidence

Отдельный Startup нужен только при повторяющемся evidence, что утверждённый рабочий пакет слишком велик или неудобен для запуска. Один технический перенос ветки такого evidence не создаёт.

## 5. Temporary capability handoff

**Статус:** 🟡 проверять следующей реальной передачей

Наиболее ясный будущий кейс — Research: Project Overview временно помогал восстанавливать и проектировать Research System, но не является постоянным Research leader.

При появлении следующего owner/leader нужно проверить, что durable artifacts позволяют:

- понять purpose и state системы;
- увидеть developmental provenance;
- принять следующий вопрос без повторного изобретения архитектуры;
- освободить Project Overview от временного ownership;
- выполнить Scale Recovery.

## 6. Role indicator

**Статус:** 🟡 pattern принят для Project Overview; переносимость требует практики

```text
▶ Project Overview — основная роль
⏸ Temporary capability — приостановлена
■ Emergency role — выключена
```

Наблюдать, помогает ли индикатор различать основную и временную работу без административного шума. Не развивать его в отдельную систему статусов.

## 7. Snapshot practice

**Статус:** 🟡 рабочая практика

Post-audit Snapshot должен стать новым поколением после Recovery Snapshot от 31 августа 2026 и сохранить:

- post-audit identity;
- новые capabilities;
- role map;
- distinctions выходов;
- состояние long-term validation;
- Coordinates of Return.

Исторический Snapshot не изменять.

## 8. Project Map

**Статус:** 🟢 проверена; отдельной нормализации сейчас не требует

`Project_Map.md` остаётся минимальной Background Map роли и не заменяет активную `MASTER_ROADMAP.md`.

Следующий Review нужен только если:

- исчезнет или появится project-level capability;
- изменится существенный ownership;
- карта перестанет помогать Return после Deep Dive;
- она начнёт дублировать Development Map.

## 9. Documentation maintenance

Material Review запускается при:

- принятии нового фундаментального authority framework;
- role-boundary failure;
- repeated routing failure;
- невозможности восстановить capability из документации;
- росте ручной интеграционной нагрузки Owner;
- meaningful long-term Re-entry;
- material change самой роли.

Не пересматривать пакет по календарю и не создавать новый permanent document ради полноты.

## 10. Следующая контрольная точка

Следующая обязательная точка развития — **Long-term Re-entry test** после реального временного интервала.

До неё роль используется operationally; новые observations сохраняются без автоматического redesign документации.

Главный guardrail:

> **Не строить более сложную Continuity-систему, чем требуется для того, чтобы Owner мог не носить весь проект в памяти.**
